# VINGO — Дорожная карта

Статус продукта подбора автозапчастей по VIN/госномеру. Обновляется по мере работы.

## Архитектура
- Монорепо на Bun: `backend` (Hono + Prisma + PostgreSQL), `webapp` (Vite + React + TanStack + shadcn), `mobile` (Expo, standalone), `packages/contracts` (Zod), `website` (Astro).
- Единое backend-ядро для веба, Telegram-бота и мобильного.
- Слои провайдеров (мок сейчас → реальные API позже без переписывания): `CatalogProvider` (VIN→OEM), `SupplierProvider` (номер→предложения), `PlateProvider` (госномер→VIN), `PaymentProvider` (мок + ЮKassa).
- Деньги в копейках (int) + валюта. Наценка — в базисных пунктах (`markupBps`, 10000 = 100%). Локальная БД — нативный PostgreSQL 18 (:5432).
- **Продуктовая модель (с 2026-09-03):** VINGO — рабочее место приёмщика небольшого автосервиса.
  Каждый пользователь состоит в **организации (СТО)**: общий гараж машин клиентов, клиенты,
  заказы и наценка. Роли: платформенная `USER/OPERATOR` (оператор = сотрудник VINGO: видит все
  заказы, ведёт их по жизненному циклу, отвечает на заявки эксперту) и внутри СТО `OWNER/MEMBER`
  (владелец меняет настройки и наценку). Позиция заказа хранит **закупочную** цену (что платит
  СТО, по ней идёт оплата и чек) и **цену для клиента** (закуп × наценка, правится вручную) —
  из них считаются смета и маржа.

## ✅ Реализовано

### Этап 1 — Поиск
- VIN → авто, госномер → VIN (с нормализацией латиницы→кириллицы), поиск запчастей, предложения.
- Раскладка по 3 тирам «Эконом / Оптимальный / Оригинал» (`tiering.ts`).

### Этап 2 — Кабинет (БД + авторизация)
- Авторизация (refresh-токены, `requireAuth`).
- Гараж (сохранённые авто), корзина (цена авторитетна с сервера), заказы.
- Жизненный цикл заказа: `DRAFT → PLACED → PAID → PROCESSING → READY → COMPLETED` (+ `CANCELLED`), карта переходов в контрактах.

### Этап 3 — Оплата
- Мок работает end-to-end (`/pay`), `YooKassaPaymentProvider` готов (активируется `YOOKASSA_*`).
- Идемпотентность, авто-переход заказа в PAID, webhook.

### Этап 4 — Telegram-бот
- Long-polling, без новых зависимостей, переиспользует `CatalogService`. Поиск по VIN/госномеру → тиры.

### Этап 5 — Мобильное (Expo)
- MVP: вход + поиск (VIN/госномер) + тиры. Запуск на телефоне через Expo Go.

### Этап 6 — Перенос из прототипа (2026-09-01)

Python-прототип [vitogrand-ai/vingo](https://github.com/vitogrand-ai/vingo) заморожен;
его наработки перенесены сюда. Что именно:

- **Словарь автожаргона** (`backend/src/catalog/part-jargon.ts`) — 1015 форм →
  622 канонических термина. Подключён в `CatalogService.searchParts`, поэтому
  «гранатку» и «воздухан» одинаково понимают веб, бот и мобильное. Ответ поиска
  дополнен полем `resolvedQuery` — по какому термину реально нашлось.
- **Каталог PartsAPI/TecDoc** (`backend/src/catalog/partsapi-provider.ts`) —
  боевая интеграция (не скелет): VIN → carId → дерево товарных групп на русском →
  применимые артикулы. Включается `PARTSAPI_KEY`. ⚠️ Нужен российский IP.
- **Фото-VIN** (`backend/src/bot/vin-ocr.ts`) — снимок шильдика/ПТС → VIN через
  Claude Vision по уже имеющемуся `ANTHROPIC_API_KEY`.
- **Голосовые** (`backend/src/bot/voice-transcribe.ts`) — расшифровка через
  OpenAI Whisper по `OPENAI_API_KEY`; без ключа бот просит написать текстом.
- **Регламент ТО** (`backend/src/garage/service-intervals.ts`) — команда `/то <пробег>`
  в боте показывает просроченное и ближайшее. Признак просрочки исправлен
  относительно прототипа: там он не срабатывал никогда (следующая точка сетки
  всегда впереди пробега), теперь просрочка считается от пробега последнего ТО.
- **Брендбук** (`brand/`) — логотипы, иконки, токены. Фавикон и знак применены;
  палитра намеренно не менялась, см. `brand/README.md`.

Не переносилось осознанно: адаптеры поставщиков EuroAuto и Автоконтинент из
прототипа — это пустые каркасы без реальных HTTP-вызовов, переносить нечего.

### Этап 7 — Рабочее место автосервиса (2026-09-03)

Сделано после аудита продукта (главные пробелы: выдуманные цены без пометки, платный декод VIN
на каждый поиск, отсутствие организации/клиентов/наценки, тупик «ничего не найдено», потеря
контекста бота при рестарте).

- **Честность про данные.** Ответы `/api/catalog/search` и `/offers` несут `source`
  (`{names, demo}`), `GET /api/catalog/status` показывает подключённые источники. Веб и бот
  помечают демо-цены предупреждением — приёмщик не назовёт клиенту выдуманную сумму.
- **Кэш расшифровки VIN** в таблице `vin_decodes` (`CachingCatalogProvider`, 60 дней): повторный
  поиск по той же машине не тратит квоту parts-catalogs и $0.15 у 17vin, переживает рестарт и
  общий для API и бота. Включается только при боевом каталоге и доступной БД.
- **Организация (СТО) и сотрудники.** `Organization` + `User.orgId/orgRole`; регистрация без
  кода создаёт свой автосервис (владелец), с кодом приглашения — вход сотрудником. Гараж,
  клиенты и заказы общие внутри СТО и невидимы другим СТО (проверено интеграционными
  тестами). Старым пользователям без организации она создаётся при первом обращении, их
  гараж и заказы переезжают в неё. Роуты `/api/org` (настройки, код приглашения, переход по коду).
- **Клиенты автосервиса** (`Customer`, `/api/customers`): имя, телефон, заметка. Авто в гараже
  получило госномер, пробег и владельца (`/api/vehicles/update`); привязка корзины к авто из
  гаража подставляет клиента. В смету печатаются автосервис, клиент и машина.
- **Наценка и цена для клиента.** `Organization.defaultMarkupBps`, у позиции `saleAmount` и
  `markupBps`; `POST /api/cart/items/sale-price` — ручная цена. DTO заказа: `salePrice`,
  `saleLineTotal`, `saleTotal`, `marginTotal`, `number` (сквозной номер), `customer`.
  Корзина показывает закуп / клиенту / маржу, карточка заказа печатает «Смету для клиента»
  без закупа. Оплата и чек 54-ФЗ по-прежнему на закупочную сумму.
- **Заявки эксперту** (`ExpertRequest`, `/api/experts/requests`) — человек в цикле: в пустой
  выдаче веб и бот предлагают «Спросить эксперта», оператор платформы отвечает текстом и
  каталожными номерами в разделе «Эксперт», автор получает push/Telegram и сразу видит
  предложения по номерам. Это закрывает пробел покрытия каталогов без внешних ключей.
- **Бот.** Сессии чатов в таблице `bot_sessions` (`PrismaSessionStore`) — VIN не теряется при
  деплое; `/garage` показывает машины автосервиса кнопками (госномер · название · клиент) и
  подставляет VIN; кнопка «Спросить эксперта» в пустой выдаче; в сообщениях — номер заказа.
- **Cron `auth:cleanup`** — чистка отозванных/просроченных сессий, кодов привязки, просроченного
  кэша VIN и старых сессий бота. Запускать раз в сутки.
- **Год авто стал nullable** по всей цепочке (контракт, `Vehicle.year`, провайдеры, веб, бот,
  мобильное): европейские VIN год не кодируют, и 17vin отдавал «Год 0». Для 17vin год
  берётся из конца описания модели («… Dynamic Type 2019»), составные марки приводятся к
  читаемому виду («Mercedes-benz» → «Mercedes-Benz»).

- **Схемы узлов у 17vin (16.09.2026).** Раньше схемы отдавал только parts-catalogs. Оказалось,
  ответ поиска 17vin (оп. 5107) уже несёт `illustration_img_address`, `callout` и `cata_code` —
  адаптер их просто отбрасывал. Теперь деталь приходит со схемой, номером выноски и узлом, а
  `schemeParts` открывает весь узел (оп. 5105 `action=part`: документная для этого оп. 4005
  `action=illustration` на нашем аккаунте отвечает «配件查询参数错误» при любых параметрах,
  а `last_cata_code_level` каталог игнорирует). Картинки лежат на `http://resource.17vin.com`:
  HTTPS-зеркало `images.17vin.com` из документации отдаёт 503 на любом пути, включая корень.
  Телеграму протокол безразличен, а вот в вебе на HTTPS-странице такую схему заблокирует
  браузер — понадобится проксирование на нашей стороне.

**Диагноз прода 03.09.2026 по скриншотам заказчика.** На VPS задан только 17vin (нет
`PARTSCATALOGS_API_KEY`, `PARTSAPI_*`, `ANTHROPIC_API_KEY`, `ABCP_*`), а поиск деталей 17vin
(операция 5107) сломан на их стороне со 2 сентября: любой запрос («капот», «колодки передние»)
даёт «ничего не найдено», Citroën российской сборки (Z8T…) 17vin не знает — при этом менеджер
parts-catalogs подтвердил, что у них этот VIN открывается. Первое действие: вписать
`PARTSCATALOGS_API_KEY` в `/opt/vingo/app/backend/.env` и перезапустить `vingo-api` и
`vingo-tgbot`; после деплоя проверка — `GET /api/catalog/status` должен показать
`catalog.names = ["partscatalogs","vin17"]`. Параллельно — вопрос менеджеру 17vin про 5107.

**Диагноз прода 04.09.2026: «машину определил, запчасть не ищет».** Живьём разобрано на Subaru
Forester JF1SK7LL5MG129305 (запрос «колодки передние»). Причина в адаптере parts-catalogs:
`parts2` отдавал только детали, у которых `nameId` попал в найденные подсказкой sid, а
локализовано у этого каталога далеко не всё (`hasUniTree: false` у subaru). Передние колодки
приходят без `nameId` и с оригинальным английским названием («PAD KIT-FRONT DISK BRAKE»),
поэтому в выдачу попадали только задние — а фильтр позиции («передние») их справедливо срезал,
и мастер видел «ничего не найдено». Лечение: отбор в узле идёт и по `nameId`, и по английским
терминам запроса из словаря `part-terms`; подсказок раскрываем 5 вместо 3, узлов 6 вместо 4;
если проход не дал деталей — повтор укороченным запросом (подсказка ищет по всему справочнику
названий, а не по этой машине, и на «амортизатор передний» отвечает названием, которого у
машины нет).

**Диагноз 18.09.2026: «Jaguar — ничего не найдено».** Живьём разобрано на Jaguar XF
SAJAA04M6FPU46282 (запрос «фильтр масляный»). Машину 17vin узнаёт (`epc: jaguar`, 2014, 204PT),
а деталей не отдаёт: каталог `jaguar` в 17vin — английский, с машинным китайским переводом
рядом, и китайский термин словаря `机油滤清器` не находит ничего (деталь зовётся `Oil filter`,
машинный китайский — `机油过滤器`). Замер по всему словарю: 36 терминов из 68 на этой машине
дают ноль, то есть поиск по ней молчал почти всегда. Лечение в адаптере 17vin: русский запрос
идёт вторым проходом английским термином словаря, а поскольку на латиницу каталог отдаёт весь
список деталей машины целиком (2272 записи, одинаково на «oil filter» и на «zzzzqqq»),
английский проход — это выгрузка со своим отбором: термин целой фразой, термины по порядку от
узкого к родовому, потолок выдачи ПОСЛЕ отбора (нужная деталь стояла 2012-й), первой строкой —
деталь, названная ровно термином. Подробности и известные ограничения — в
`docs/CATALOG_ADAPTERS.md`; случаи Jaguar добавлены в `catalog:cases`. Что при этом
отвечает parts-catalogs по этой машине — с локального IP не проверить (ключ привязан к VPS).

**Отказ источника больше не роняет поиск (22.09.2026).** Истёк тестовый аккаунт 17vin, и он стал
отвечать «аккаунт просрочен» на каждый запрос. `FallbackCatalogProvider` считал любой сбой
источника сбоем всего поиска, поэтому КАЖДЫЙ промах parts-catalogs — по любой машине, не только
по тем, что знает 17vin, — превращался у мастера в 502 вместо «ничего не найдено» с кнопкой
«Спросить эксперта» (живьём: VW Golf «маслоотделитель», Subaru «турбина»). Теперь сбой
пробрасывается, только если НИ ОДИН источник не ответил; ответ живого каталога «не найдено» —
это ответ, а отказ соседа остаётся в журнале. Прежнее правило работает там, где и писалось:
когда источник один или упали все, конец предоплаты под «ничего не найдено» не маскируется.

Заодно закрыт вопрос по Jaguar: `parts-catalogs` VIN SAJAA04M6FPU46282 не знает вовсе (`[]`),
машина держалась только на 17vin. И у самого parts-catalogs снята привязка ключа к IP — корзина
`catalog:cases` теперь гоняется локально, а не только на VPS.

**Открытый вопрос к parts-catalogs (для менеджера).** У каталога `subaru` метод
`schemas?carId&partNameIds=<sid>` отдаёт нестабильный и местами явно чужой ответ: sid 289
(«Колодки тормозные дисковые») в одном замере вернул «Задний тормоз», через двадцать минут —
«Воздухоочиститель и фильтр»; sid 23 («Амортизатор подвески») — «Управляющие клапана, акпп».
Параметр `partName` на ответ не влияет, `criteria` тоже. Из-за этого одинаковые поиски дают
разный результат. Наш код от этого защищён только повторным проходом.

Не сделано осознанно: аккаунты поставщиков на организацию (модель Ta-Dam), оплата при выдаче (заказ-наряд с работами — этап 8), история статусов, Telegram-first регистрация без email,
кэш предложений в БД — см. «Предстоит».

### Этап 8 — Аудит продукта, схемы в вебе, заказ-наряд (2026-09-16)

Сделано по запросу заказчика «что не хватает, что было сломано, сравнить с конкурентами,
оценить идеи». Исследование источников — `docs/SOURCES.md`, конкурентов —
`docs/COMPETITORS.md`, классы ошибок — `docs/POSTMORTEM.md` (класс 14).

- **Граница между машинами** (идея заказчика № 3). В боте новый VIN/госномер/машина из
  гаража закрывает прошлый подбор: сбрасываются детали, предложения, схема и её узел, в
  ленте появляется «🔄 Другая машина — прежний подбор закрыт». Раньше номер выноски «9»
  после смены машины уходил в узел *прошлой* машины. В вебе поиск стал двухшаговым:
  сначала машина (VIN/госномер, недавние машины, демо-VIN только при демо-каталоге), затем
  липкая полоска текущей машины с «Сменить машину»; история запросов — по этой машине.
- **Схемы 17vin в вебе на HTTPS.** Картинки 17vin лежат только на `http://`, будущий
  HTTPS-сайт их заблокирует. Добавлен прокси `GET /api/catalog/image?src=` с белым списком
  хостов (`scheme-image.ts`), лимитом 10 МБ и кэшем сутки; веб подставляет его для
  `http://`-картинок (`webapp/src/lib/scheme-image.ts`). Дубликаты по OEM при склейке
  сохраняют картинку, позицию и узел.
- **Заказ-наряд** (идея № 4, MVP). Заказ получил работы (`OrderWork`: название, цена,
  количество), данные приёма (госномер и пробег из гаража, срок, причина обращения,
  комплектность и повреждения), «принял заказ» из сессии; организация — реквизиты
  (юрнаименование, ИНН, ОГРН, адрес, текст гарантии). Роуты `POST /api/orders/works`,
  `/works/remove`, `/reception`; правится до статуса `COMPLETED`/`CANCELLED`. Печать
  «Заказ-наряд» по составу п. 9 и п. 12 ПП РФ от 29.05.2025 № 780 (заменило ПП № 290 с
  01.09.2025): исполнитель, заказчик, автомобиль, причина, комплектность, срок, таблицы
  работ и запчастей, итого, порядок оплаты, гарантия, подписи приёма и выдачи. Смета
  печатает работы и общий итог. Без реквизитов карточка предупреждает и ведёт в настройки.
  Живьём пройдено в браузере: регистрация → гараж → поиск → корзина → работы → приём →
  реквизиты → печать → оформление (работы переживают checkout).
- **Смоук боевого адреса** `bun run --cwd backend smoke:live -- http://<адрес>`: `/health`,
  страница, `catalog.demo=false`, живой поиск по машине из корзины случаев; каждый провал
  говорит, что делать дальше. Это «три проверки после деплоя» машиной, без граблей `curl`
  с кириллицей на Windows.
- Мелочи: `/orders` в боте показывает сквозной номер заказа; история поиска до 10 машин;
  502 каталога в вебе — «Каталог сейчас недоступен».

**Идеи заказчика — вердикты.**
1. *Gemini рисует принципиальные/кинематические схемы по списку деталей* — **нет**. Нарисованная
   моделью схема — выдуманные данные в документе для мастера, а настоящие взрыв-схемы с
   выносками каталоги уже отдают (parts-catalogs и 17vin). Правильное продолжение —
   кликабельные выноски на реальной схеме (координаты `callout` уже приходят от 17vin).
   Vision-модели уместны там, где они читают, а не рисуют: VIN с шильдика (есть), накладная
   поставщика → строки заказ-наряда, фото детали → название для поиска в каталоге.
2. *Упростить интерфейс* — сделано: два шага поиска, одна машина на экране, чипы вместо форм.
3. *Отдельные вкладки на машину / отметка начала и конца* — сделано в боте и вебе (выше).
4. *Заказ-наряд по запчастям, фото накладных, текстам, голосу* — MVP сделан из
   подтверждённых человеком данных. ИИ-ввод (фото накладной, голос → черновик строк) —
   следующий этап, с обязательным подтверждением приёмщика: п. 9(е) и п. 14 ПП № 780
   требуют согласия клиента на состав и допработы, чек формирует касса (54-ФЗ, ст. 4.7).
5. *ИИ-помощник по аналогам* — **не сейчас**. Кроссы должны приходить от поставщиков (ABCP
   `crosses`, PartsAPI `getCrosses`), а не из головы модели; правило «модель не выдумывает
   номера» действует.
